# 왜 모델링이 어려운가?

1. 알아야 하는 것이 많다.
    - 데이터 본질 이해
    - 모델링 기본 지식 (엔터티, 관계, 속성 정의 등)
    - DBMS 구체적 특징과 기능 등
        - DBMS별 장,단점 (특징)
        - SQL 작성 능력
        - PLAN 분석 능력
2. 정답이 없다.
    - 공식이나 틀에 맞추기보다 상황에 따라 판단이 달라져 정답이 없이 느껴짐
        - But, 상황에 맞는 정답(모범 답안)은 존재한다.
3. 구축된 모델을 설득하는 과정
    - 사용자와 개발자를 설득해야 한다.
        - 데이터 집합을 정의한 개념적 내용을 설명하고 이해시켜야 한다.
    - 이미 익숙해진 모델을 바꾸도록 하는 것은 어렵기 때문

# 모델링은 상식적이다.
> 데이터 모델링은 상식적 이론이 토대가 되어야 하며, 상식을 기반으로 한 경험이 쌓여야 좋은 모델을 만들 수 있다.
- 모델링 이론은 상식적이나, 실제로 적용은 쉽지 않다.
    - 데이터 무결성을 최우선으로 생각하기에 이론은 상식적일 수 밖에 없다.
- 이를 잘 하기 위해 이론과 경험이 모두 필요하다.

# 모델러와 바둑 프로기사
- 모델링과 바둑은 유사하다.
    1. 정석을 모르면 제대로 하기 어렵다.
        - 모델링도 엔터티, 속성, 관계, 정규화 등 이론을 잘 숙지해야 잘할 수 있다.
    2. 이론 뿐만 아니라 경험을 기반으로 다양한 상황에 따른 선택을 해야한다.
- 이를 위해, 분석력, 논리력, 종합적 사고능력, 설득력, 섬세함 등이 있어야 한다.

# 좋은 모델이란?
> 사용자가 원하는 데이터를 정확하고 빠르게 보여줄 수 있는 단순한 모델
1. `단순`하고 `명확`한 모델 ([명확한 모델이란?](#명확한-모델이란))
    - 모르기때문에 복잡하게 만드는 것. 단순하게 만들어라.
2. `데이터 무결성`(Integrity)이 보장되는 모델([데이터 무결성 보장 방법](#데이터-무결성을-보장하는-방법))
    - 모델링의 최우선 목표 : `데이터 무결성을 보장`하도록 `데이터 모델을 구축`하는 것
3. 성능이 좋은 모델
    - 가끔 상황에 따라 데이터 무결성을 다소 포기해야 하는 경우가 생길 수 있다.
    - 사용자는 빠른 결과를 원하므로, 성능을 무시하는 모델은 좋은 모델이 아니다.
4. 비즈니스를 효율적으로 표현한 모델
    - 아래 문제를 조심하자. 
        1. 비즈니스 요소 누락
        2. 필요없는 비즈니스 모델에 표현
    - 필요한 요건만 데이터로 관리
5. 업무 변화에 유연하게 대처할 수 있는 모델
6. 가독성이 좋고, ERD 표기법에 맞는 모델

### 명확한 모델이란?
- 명확한 정의가 된 모델
- 특히 엔터티에 대한 명확한 정의
    - 잘못된 정의는 잘못된 사용으로 이어짐

### 데이터 무결성을 보장하는 방법
- 가장 기본 : `중복`제거
    - 중복 속성, 중복 엔터티 제거

# 모델링이 필요한 이유

- 필요성
    1. 데이터를 분석하는 과정을 지원, 관련자의 커뮤니케이션을 돕는다.
        - 모델링 과정 중의 모델은 업무와 데이터를 분석하는 데 중요한 역할을 한다.
    2. 사용자의 요구사항을 반영하는 작업, 관련자가 모델을 이해할 수 있도록 함
        - 애플리케이션 개발 중 모델의 변경을 최소화할 수 있도록 하는 과정이 모델링
        - 모델링을 거치지 않으면 좋은 품질의 모델이 나오기 어렵다.
    3. 데이터를 정확하게 관리, 사용자에게 빠르게 제공
        - 단순 확장성 뿐만 아니라, 데이터를 잘 관리하는 것이 모델링의 목표
        - 정확한 정보를 빠르게 제공하고 업무를 신속하게 진행하기 위해서는 좋은 모델이 필요하다.
    4. 데이터 모델링 자체가 프로젝트의 분석/설계를 주도적으로 이끈다.   
        > 구현 단계의 위험을 최소화하기 위해 모델링이 필요하다.
        - 대규모 프로젝트에서 시스템의 터를 잡고 뼈대를 세울 수 있도록 모델링이 필요하다.
        - 요구 사항이 변하더라도 모델 구조는 변하지 않고, 속성 변경만 발생할 수 있도록 모델이 구축되어야 한다.

# 좋은 모델러란?
> 기술력과 분석력을 모두 갖춘 사람
1. 기술력
    - 모델링 이론을 깊이 이해
    - RDBMS에 대해서 깊이 이해
        - 데이터 모델링은 테이블로 구현될 때까지의 전반적 과정을 의미하기 때문
    - 튜닝
        - 데이터를 정확하고 빠르게 제공하려면 튜닝 요소를 알고 모델링에 적용할 줄 알아야 한다.
2. 분석력
    - 정확한 분석을 통해 모델의 기반이 되는 엔터티 정의
    - 속성 하나의 쓰임새도 업무와 연관지을 수 있어야 한다.
3. 설득력
    - 다양한 이해 관계자와 많은 협의를 해야 하고 설득해야 할 때가 많기에 설득력이 중요하다.
4. 발표력
    - 자신이 구축한 모델을 많은 사람들에게 설명해주고 이해시켜야 한다.
5. 경험
    - 틀에 맞지 않는 상황이 많아서 경험에 의존해야 할 때가 많아, 최종 판단 기준이 경험이 될 때가 많다.
6. `사명감`
    - 모델러가 시스템 전체에 미치는 영향은 크다.
    - 따라서 더 효율적인 시스템이 될 수 있도록 사명감을 갖고 해야한다.
    - 항상 `데이터 무결성`과 `데이터베이스 성능을 만족`하게 하는 모델을 만들려고 노력해야 한다.
        - But, 현실적인 자원의 이유로 모두를 만족할 수 없을 수 있다.
            - 이때는 `데이터 구조`를 잡고 `중복 속성을 제거`하는 것에 목표를 갖자.
                - 데이터 구조가 모델러가 해야 할 핵심적인 역할이기 때문
                - 뼈대가 튼튼하고 확장성이 좋은 모델을 구축하는 모델러가 좋은 모델러

# 모델링 목표
> 데이터 무결성과 DB 성능 향상, 유연한 모델 만들기
1. 데이터의 무결성을 높이는 것
    - 데이터 결점
        1. 데이터 자체가 틀린 것
        2. 데이터끼리 서로 일치하지 않는 것
        3. 관계 속성이 부모 엔터티 주 식별자에 존재하지 않는 값을 가지는 것
            - ex, 입금액에 '천원' 문자로 입력 등
        4. 데이터 중복
            - 데이터 값의 중복
                - 같은 값을 의미하면서 여러 곳에 존재
            - 같은(유사한) 속성이 여기저기에서 사용
                - 속성이 반복적으로 사용되는 것은 바람직하지 않다.
                    - 엔터티를 통합해 서브타입으로 관리하는 것이 좋다.
            - 다만, 중복을 제거하며 성능 문제가 생길 수 있다.
2. 성능 이슈가 발생하지 않도록 하기
    - 대부분 성능 문제는 심각하지 않은 경향이 있어 성능 문제에 매달리는 것도 바람직하지 않다.
3. 유연한 모델
    - 정규화와 일반화를 할수록 확장하기 좋은 모델이 된다.
        - 유사하지 않은 데이터를 나누기
        - 유사한 데이터를 통합하기
    - 이때, 업무 사용 용도를 판단 기준으로 두지 말고, 데이터 자체를 판단 기준으로 두자.
        - 유사한 데이터라면 통합된 모델이 확장성이 좋은 모델
        - 보통 통합된 모델 분리가 통합보다 수월하므로, 통합하는 방향으로 모델링 목표를 세워야 한다.
4. Application에 독립적인 모델
    - 데이터 성격에 맞는 엔터티가 정의되었다면, Application 수정에 따라 모델이 변경되지 않는다.
    - 화면에서 보려고 하는 것은 DB View로 대부분 해결
        - View를 잘 사용하면, Application과 모델을 독립적으로 관리할 수 있다.
5. ERD로 잘 표현된 모델을 구축하는 것
    - 가독성이 좋은 모델이 이해하기 쉽고, 커뮤니케이션에 도움을 준다.
    - 엔터티/속성 정의도 단순하고 명료해야 모델의 이해와 커뮤니케이션을 돕게 한다.
